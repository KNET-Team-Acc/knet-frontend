# KNET frontend

Vite + React 19 + Tailwind. React monta el layout (`src/components/`); casi toda la lógica vive en el motor vanilla `src/lib/engine/knetApp.js` (`bootKnetApp()`). Landing 3D: `src/lib/cinematic/universe.js`. Datos estáticos: `src/data/` (`config.js` tiene `LEGAL`, `KEY`, `CONSENT_KEY`, `PREF_KEY`). Backend: `../knet-backend` (ver su `CLAUDE.md`).

## Comandos
- `npm run dev` (:5173) · `npm run build` (verificación mínima tras editar) · `npm run lint` (`knetApp.js` está ignorado por eslint)
- `npm run e2e` (Playwright + API simulada en `e2e/support/mock-api.js`; build en `dist-e2e`, preview :4173) · `npm run e2e:real` (contra knet-backend; `E2E_API_URL`, preview :4174). El CI corre lint, build y e2e: mantenlos verdes.
- Despliegue: `vercel.json` / `public/_headers` / `public/_redirects`. Cabeceras: fuente única `deploy/security-headers.js` (la usa `vite preview`); si cambian, actualiza las copias estáticas. La CSP prohíbe scripts inline y `eval`.

## i18n
Español es la fuente; el inglés se aplica en tiempo real. `src/lib/i18n/dictionary.js` = frases exactas (`EXACT`, clave = texto ES). `src/lib/i18n/runtime.js` = `PATS` para textos con variables: `[regex estilo re.escape con ([\s\S]*?), "EN con {0}", longitud del ES sin marcadores]`. Si cambias un texto visible en ES, actualiza su entrada o deja de traducirse. Textos con clave (`t("…")` en el motor) van en `I18N.es`/`I18N.en` de `src/data/navigation.js` (p. ej. `inv.*`, pestaña Invitaciones de Mis eventos, `meView = "invites"`: `invSegHTML`, `invitesHTML`, `invPending`; `org.*`, panel de creador, en `ORG_ES`/`ORG_EN`; `sim.*`, «Vista previa de tu evento» de la landing: usa `st()` porque se pinta antes de declarar `LANG`/`t()`, y `applyLang()` la repinta con `simRelang()`).

## API (`src/services/api.js`)
- Base `VITE_API_URL` (sin definir: `http://localhost:4000` en desarrollo y modo local en un build de producción; vacía = solo local, sin cuenta).
- Sesión: `api.signUp` / `api.login` / `api.exchange` (vuelta de LinkedIn) guardan access + refresh token en `localStorage["knet-auth"]` y cada petición va con `Authorization: Bearer`. Un 401 refresca **una sola vez** (un único refresh en vuelo) y repite; si el refresh falla se borra la sesión y se emite `session-expired` (`onApiEvent`). Un 409 `legal_outdated` emite `legal-outdated`.
- Solo en desarrollo y sin sesión: `X-User-Id` desde `localStorage["knet-api-user"]` o `VITE_DEMO_USER_ID` (si no, el demo compartido). `request(..., { userId })` fuerza otra cuenta (Bearer si es la de la sesión; si no, solo en desarrollo). `accountAvailable()` = hay con quién hablar con `/api/me`.
- Cuenta KNET en el motor (`openEntry`, `openAuth`, `enterWithAccount`): con API, entrar pasa por `#m-auth` (`AuthModal.jsx`); «Continuar sin cuenta» = flujo local de siempre. El perfil local queda ligado a `A.accountId` y solo se sincroniza si coincide con la sesión (`accountReady()`). Registro con perfil local sin cuenta → se vincula y el navegador sube todo; login → manda el servidor (`A.apiLinked = true`).
- LinkedIn real: si `/api/auth/providers` dice `linkedin: true`, la pantalla de permisos navega a `/api/auth/linkedin` (scopes marcados) y la vuelta llega con `?knet_auth=<código>` (`authReturn()`). Sin configurar, se mantiene la importación simulada del modo local.
- Re-aceptación legal: `#m-legalup` (`LegalUpdateModal.jsx`, `data-locked`: ni Escape ni el fondo lo cierran) registra una `aceptacion` en la cadena local + servidor antes de seguir.
- Fallback silencioso: `ApiOffline` (red, timeout 4 s, 503) → el motor sigue con lo local; `ApiError` = error HTTP.
- Panel de creador (`src/lib/engine/organizer.js`, `createOrganizer(ctx)`; este archivo sí pasa por eslint): «Mis eventos › Mis eventos creados» (`meView === "creator"`, hash `#creador`) solo si `isOrganizer()` (`A.accountRole` organizer/admin, de `/api/me` en `applyServerUser`, + `accountReady()` + `A.apiLinked`). Pasos `ORG_STEPS` contra `api.admin.*` (`/api/admin/*`); cada paso guarda en el servidor (borrador) y publicar llama a `syncFromApi()`. Lo que se guarda en la ficha va en español. Admin (`A.accountRole === "admin"`, `ctx.isAdmin()`): selector «Mis eventos / Todos los eventos» (`st.scope`, `api.admin.listEvents({ all })`) para ver y editar los de cualquier organizador (`owner`, aviso `.is-admin` al editar uno ajeno); los `catalog: true` salen en solo lectura. La cuenta admin es de gestión (`isAdminMode()`): solo «Mi cuenta» (`adminPerfilHTML`, sin permisos MCP) y «Panel de eventos» (`adminEventsHTML`: panel, recintos y catálogo); `ADMIN_TABS`/`ADMIN_VIEWS`/`adminRoute()` redirigen el resto, `ADMIN_NO_ACTS` quita inscribirse, check-in, misiones, conectar y escanear (el backend responde 403 `admin_account`), sin tour ni XP. Textos `adm.*`. Errores: validación local y de la API se pintan en su sitio (`fail`/`paintMsg`) sin repintar, para no perder lo escrito; `org.dirty` evita que `refresh()` repinte el formulario a medio llenar; 403 `forbidden_role` → `onRoleLost()`. Sin rol, «Crear un evento» (`openNewEv`) sigue siendo la propuesta local de siempre. Textos: claves `org.*` de `I18N` en `navigation.js`.
- Eventos `hosted` (creados en el panel): `addApiEvent` los acepta sin `sourceUrl`; el detalle trae `sessions` y `missions` (`apiSessions`/`apiMissions`, guardadas en `A.apiEvents`). `sessionsFor()` usa esa agenda oficial (ids = códigos del servidor; `sessionById` busca por id) y sus misiones salen en «Misiones de tus eventos» (`eventMissions()`, fuera de `activeMissions()`). Ojo con el arranque: `addApiEvent`/`sessionsFor` corren antes que muchas `const` del motor (TDZ).
- Catálogo: `src/data/events.js` solo tiene eventos reales con fuente oficial (`MAIN_EV` = evento principal; `EV_ALIAS` migra ids retirados, p. ej. `bog` → `and`). `mergeEvents()` actualiza los conocidos con `GET /api/events` e integra los nuevos (solo `kind: "real"` con `sourceUrl` http(s)) en `A.apiEvents`, con ficha y recinto de `GET /api/events/:id` (`loadApiEventDetail`); si la API deja de publicarlos se retiran. Todo texto de la API pasa por `apiTxt`/`apiUrl`/`apiDeep` antes de entrar a `EVENTS`, `EV_INFO` o `VENUES` (varias plantillas lo insertan sin escapar).
- IA (`api.aiChat`, `aiSimulate`, `aiDossier`, timeout `AI_TIMEOUT_MS` = 30 s): `ask()` (Concierge), `sendDm()` (Simulador) y la acción `gen` (Dossier) prueban primero el servidor (`aiConcierge`, `aiSimulator`, `aiDossierGen`, solo con `accountReady()` y `A.apiLinked`) y, ante `ApiOffline` (incluye 503 `ai_unavailable`) o cualquier error, usan `reply()` / `dmReply()` / el Dossier local sin mostrar error. Mientras responde se bloquea el formulario (sin envíos dobles). El Dossier de la IA se guarda en `A.aiDossier[evento]` (lo usan `dossierData()` y el PDF) y ya queda en el servidor, así que no se reenvía por la cola; el local sigue yendo por `outbox` (`dossier`).
- XP híbrida: `A.xp = xpServidor + A.xpLocal`. `A.xpSynced` (claves `mission:`, `checkin:`, `conn:`, `coffee:<id del servidor>`) evita restar dos veces al confirmar el servidor.
- `A.outbox`: acciones offline (`mission`, `reg`, `checkin` (con `method` qr/nfc), `conn`, `dossier`, `coffee`, `dm`) reenviadas en orden por `flushOutbox()`; `A.apiLinked` decide quién manda en el sync.
- Cafés y DMs (`proposeCoffee`, `answerCoffee`, `sendDm`): `A.coffees[nombre]` guarda `sid` (id del servidor), `role` (proposer/invitee), `real` y `xpLocal` (sus +50 XP se sumaron en local → `coffeeXpSynced()` los pasa al servidor una vez). `A.dms[nombre][i].sid` marca los mensajes ya subidos. Sin cuenta los DMs no se encolan (`apiRun(op, { localQueue: false })`): `linkLocalToApi()` sube los pendientes. Usuario real = `connIndex.get(n).userId` o `A.qrConn[].userId` (`isRealPeer`): no hay respuestas simuladas y se responde desde el chat; con contactos del catálogo `scheduleResponses()` / `dmReply()` siguen simulando y la respuesta del café se registra en el servidor. `syncFromApi()` baja cafés y los hilos con usuarios reales (404 = backend sin esos endpoints → se ignora). Tiempo real: `startStream()` abre `/api/me/stream` (SSE, token en `?access_token=` vía `streamUrl()`); `message.new` se une al hilo y el resto lanza un sync.
- Solicitudes recibidas (`A.inbound[nombre] = { at, from: match | api, sid, userId }`, `A.inboundGone` = rechazadas, `A.inboundSeeded` = industria ya sembrada): `seedInbound()` hace que un match afín del catálogo te escriba una vez por industria (tras `syncFromApi` o `scheduleResponses`). `acceptInbound` = `award` + `apiRun({ t: "conn", state: "accepted" })` (POST pendiente + PATCH, o solo PATCH si trae `sid`; +100 XP una vez por `conn:<nombre>`); `declineInbound` borra en el servidor solo si hay `sid`. Se pintan con `inboundHTML()` en «Mi red», el modal de conexiones, `personActions` y `matchActions`. SSE `connection.request`: `onLiveRequest` solo la toma como entrante si viene `status: "pending"` + `direction: "incoming"` (el backend aún no lo emite); si no, `liveSync()`. El E2E siembra `inboundSeeded: "tech"` en `seedSession` para no recibir la solicitud automática.
- Notificaciones: `notify(type, title, sub, extra)` fusiona `extra` en el objeto. La de encuesta lleva `hid` (id de `A.history`): `data-nsurvey` abre `openSurvey(hid)` y `resolveSurveyNotif()` la marca `done` al enviarla.
- Intereses: catálogo por categorías en `src/data/interests.js` (`INTEREST_CATS`, `INTEREST_EN` solo para la etiqueta; lo guardado es el texto ES) + tags de `EVENTS` + `BASE_P` (`interestGroups()`). `interestPickerHTML(attr, id, errId, selected)` (onboarding `#pf-ints`/`data-int`, edición `#pfeInts`/`data-eint`) con buscador `#<id>-q`, filtro `data-icat` e intereses propios (`data-iadd`, máx. `INTEREST_CUSTOM_LEN`); el límite 1–5 se valida en `pickerToggle`/`pickerAdd`.
- AI Concierge: `bubble()` pinta `.msg` (avatar + burbuja) y `citesHTML(m.src)`; `aiConcierge()` devuelve `{ html, src }` con `sources` del servidor saneadas o, si no vienen, los títulos de `sessionsFor` presentes en el texto (`citedSessions`/`linkCites`). La acción `agses` (`openAgendaSession`) abre la agenda en el evento/día de la sesión (`goto` no sirve: el código lleva `:`) y enfoca `.agenda-item[data-ses]`. Sugerencias `conciergePills()`: `data-v` = pregunta ES (la entiende `reply()`), `data-l` = la del idioma activo (`ask(q, shown)`). Textos nuevos: claves `req.*`, `dm.*`, `notif.*`, `int.*`, `ai.*` (`NET_ES`/`NET_EN` en `navigation.js`); estilos en `src/styles/main/09-network-concierge.css`.
- Solicitudes entre usuarios reales (knet-backend#24): `A.requests[n]` con `real: true` (`userId`, `via: dir | qr`, `headline`) = solicitud enviada que solo responde la otra persona (`scheduleResponses` no la simula; se lista en `sentHTML()` con «Cancelar» = DELETE). Directorio «Asistentes de {evento activo}» (`attendeesHTML`, `loadAttendees`, estado en memoria `att`; `GET /api/me/attendees`, 404 = backend sin directorio → no aparece): «Conectar» = `connectAttendee` → `apiRun({ t: "conn", state: "pending", peerUserId, eventId })` (`sendConnection` hace POST con `peerUserId`; aceptada al instante = solicitud mutua → resync). Aceptar una entrante real (`acceptInbound` con `op.real`) crea la ficha en `A.qrConn` (`addPeerCard`); si la solicitud ya no existe (404/403) se deshace con `revertRealAccept`. `syncRealRequests()` reconcilia en cada sync (pendientes `direction: "outgoing"` → `A.requests`; las que el servidor ya no tiene se quitan salvo si esperan en `A.outbox`). SSE `connection.removed` (`onLiveRemoved`) retira la solicitud sin aviso (el rechazo es silencioso). Identidad por nombre: ver knet-frontend#33.
- Ranking de Misiones (`leaderboardHTML`, `#lbCard`): `GET /api/me/leaderboard` (`api.leaderboard`, `loadLeaderboard`) con pestañas `data-lbscope` «Todo el evento» / «Mis conexiones» (`lb.scope`); caché en memoria `lb` por evento|scope (60 s, `lb.at = {}` en cada sync). `board(scope)` → `{ rows, total, live }`: tu fila usa `A.xp` y el orden se recalcula en local (empates = misma posición). Sin `attReady()`, sin evento o 404 (`lb.missing`): solo tú. La insignia Top 3 usa siempre el del evento. Textos `lb.*` (`LB_ES`/`LB_EN`).
- QR/NFC: con cuenta sincronizada (`qrLiveMode()`) la credencial de «Mi red» (`redCredHTML`) pinta el token de `GET /api/me/qr-token` con `qrcode-generator` y lo renueva cada `refreshIn` s; «Escanear» abre la cámara (`startCamScan`: `BarcodeDetector` o `jsqr` cargado bajo demanda) y envía el token a `POST /api/me/connections/scan` (`adoptScan`; errores `own_qr`/`qr_expired`/`qr_used`… en `scanErrText`). Respuesta pendiente (backend con knet-backend#24) = solicitud enviada (`scanSent`, sin XP hasta que la otra persona acepte); aceptada (backend anterior o solicitud mutua) = `scanDone` con la XP del servidor. El mock usa `scanAccepts: true` para el comportamiento anterior. Offline se encola como `conn` con `state: "scan"` solo si el token sigue vigente (`qrTokenExpiry`); si caduca antes de reenviarse, se avisa. Sin API / sin cuenta / backend sin el endpoint: QR decorativo y `simulateScan()` con `SUMMIT_POOL`. Check-in NFC (`nfcCheckin`) solo si existe `NDEFReader`: el tag lleva `knet:checkin:<evento:día:slot>` (texto) o una URL con `#checkin=<evento:día:slot>`.
- Consentimientos: cadena local en `knet-consent-local` + `POST /api/me/consents`. `rec.api` (pendiente/guardado/rechazado) se escribe tras el hash y `verifyChain()` lo excluye. Cada pendiente se envía como la cuenta que lo dio (`rec.cuentaId`); sin una sesión de esa cuenta espera (`consentSendable`, nunca se marca «rechazado» por falta de sesión). `logConsent(evt, { savedOnServer })` deja constancia local de algo que el servidor ya registró (registro de cuenta, LinkedIn). Registros sin `rec.api` (anteriores) no se suben.
- «Revocar y borrar mis datos»: borra local, espera el `revocacion` y llama `DELETE /api/me`; si está offline guarda el UUID en `knet-pending-erase` (y conserva la sesión solo para ese reintento) y `syncFromApi()` reintenta tras `flushConsents()`. Al completarse se cierra la sesión. 403 `demo_account` = solo borrado local.
